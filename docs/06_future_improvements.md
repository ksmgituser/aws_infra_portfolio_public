## 3.1. メンテナンス表示機能の未実装

### 背景

現状、RDSのメンテナンスやフェールオーバー中にユーザーがアクセスした場合、アプリケーションエラー画面が表示される。計画メンテナンス時やインフラ障害時に意図したメンテナンス画面を表示する手段がなく、ユーザー体験の観点で課題がある。

### 対応方針

以下2つの方式を組み合わせて実装することを想定する。

**方式① ALBカスタムエラーレスポンス（インフラ障害時）**

ECSタスクのヘルスチェックが全滅した際に、ALBのデフォルトアクションとして503固定レスポンス（メンテナンス用HTML）を返す設定を追加する。ECSタスクが停止している状態でも機能するため、インフラ障害時のフォールバックとして有効。

**方式② Laravelメンテナンスモード（計画メンテナンス時）**

Laravelの組み込み機能（`php artisan down`）を利用し、計画メンテナンス時にアプリケーション層でリクエストを503でブロックする。ECS Execを経由してコンテナ内でコマンドを実行する運用手順をRunbookとして整備する。

なお、Fargate環境ではタスク再起動時にメンテナンスモードのフラグ（`storage/framework/down`）が消えるため、SSM Parameter Storeにフラグ値を保持しLaravelミドルウェアで参照する方式を採用する。

### 優先度

中（サービス品質に影響するが、ポートフォリオ用途では即時対応は不要）

### 対応時期

機能拡張フェーズ（インフラ基盤の安定稼働確認後）


## 3.2. VPCエンドポイント1AZ配置によるリスク

### 背景

コスト削減を目的として、Interface型VPCエンドポイント（ECR・SSM・CloudWatch Logs）をap-northeast-1aのみに配置している。（基本設計書 5.6参照）

ap-northeast-1aのエンドポイントに障害が発生した場合、ap-northeast-1cで稼働中のECSタスクからECR・SSM・CloudWatch Logsへの通信が途絶するリスクがある。具体的には以下の影響が想定される。

- 新規タスク起動時にECRからイメージを取得できず起動失敗
- SSM Parameter Storeから環境変数を取得できずアプリが起動しない
- CloudWatch Logsへのログ出力が停止

なお、ap-northeast-1cで稼働中の既存タスクは、起動済みであればイメージ取得・SSM参照は不要なため即時影響は受けない。

### 対応方針

コスト増を許容できるタイミングで、ap-northeast-1cにもInterface型エンドポイントを追加配置し2AZ構成に変更する。

Terraformのモジュール化により、`var.enable_vpce_1c = true` のような変数1つで切り替えられる設計を目指す。月額追加コストは約$40の見込み。（基本設計書 5.6参照）

### 優先度

低（ポートフォリオ用途ではエンドポイント障害の可能性は極めて低く、発生時はTerraformで即時切り替え可能）

### 対応時期

本番運用移行時（コスト増を許容できるタイミングで対応）


## 3.3. terraform-userのアクセスキー管理

### 背景

現状、ローカルからTerraformを実行するために`terraform-user`のIAMアクセスキーを発行し、ローカル環境の`~/.aws/credentials`に保存している。アクセスキーは永続的な認証情報であり、以下のリスクを抱えている。

- 誤ってGitリポジトリにコミットした場合の漏洩リスク
- ローカル環境が侵害された場合の不正利用リスク
- 90日ごとの手動ローテーションが必要（運用設計書 6.1参照）

また、GitHub Actionsからのインフラ操作はOIDCによるIAMロールAssumeに移行済みだが、ローカル実行分はアクセスキー方式のままとなっている。（運用設計書 1.6参照）

### 対応方針

AWS IAM Identity Center（旧AWS SSO）を導入し、ローカルからのAWSアクセスもアクセスキー不要の一時認証情報方式に移行する。これにより`terraform-user`のアクセスキーを廃止できる。

移行後は`aws sso login --profile portfolio-dev`で認証し、一時的な認証情報を取得する運用に変更する。認証情報は数時間で自動失効するためローテーション運用も不要になる。

なお、IAM Identity Centerの導入にはAWS Organizationsが必要となるため、シングルアカウント構成である現状では追加設定が必要になる点に留意する。

### 優先度

中（漏洩リスクは存在するが、ローカル環境の管理で一定程度軽減可能。チーム開発・本番運用移行時には優先度が上がる）

### 対応時期

本番運用移行時またはチーム開発への移行時


## 3.4. RDSパラメータグループのデフォルトからカスタムへの変更

### 背景

基本設計書 7.7にてカスタムパラメータグループの設計を定義しているが、現時点ではデフォルトのパラメータグループのまま運用している。

デフォルトパラメータグループには以下の問題がある。

- 文字コードが`latin1`のままとなっており、日本語データを投入した場合に文字化けが発生する可能性がある
- タイムゾーンがUTCのままとなっており、ローカル環境（`Asia/Tokyo`）との差異が生じる
- スロークエリログが無効なため、パフォーマンス問題の検知ができない
- デフォルトパラメータグループはAWS管理のため変更不可であり、設定変更には必ずカスタムパラメータグループへの差し替えが必要

### 対応方針

基本設計書 7.7で定義済みのカスタムパラメータグループを作成し、RDSインスタンスに適用する。

Terraformで`aws_db_parameter_group`リソースを追加し、`aws_db_instance`の`parameter_group_name`に紐付ける。パラメータグループの変更はRDSの再起動を伴うため、メンテナンスウィンドウ内での適用を推奨する。

適用するパラメータは以下の通り。（基本設計書 7.7参照）

| パラメータ | 値 |
| --- | --- |
| `character_set_server` | `utf8mb4` |
| `collation_server` | `utf8mb4_unicode_ci` |
| `time_zone` | `Asia/Tokyo` |
| `slow_query_log` | `1` |
| `long_query_time` | `1` |

### 優先度

低（ポートフォリオ用途では日本語データの投入がなければ即時影響はなく、許容範囲と判断）

### 対応時期

機能拡張フェーズ


## 3.5. Terraformモジュールの単体テスト未実装

### 背景

本ポートフォリオではインフラ構築とCI/CDの動作確認をスコープとし、Terraformモジュールの単体テストは実装していない。現状では `terraform fmt`・`terraform validate`・`tflint`・`terraform plan` によるコード品質チェックのみを行っており、モジュールが意図通りのリソースを生成するかの検証手段がない。

チーム開発や本番運用を見据えた場合、モジュールの変更が意図しない影響を与えないことを自動的に保証する仕組みが品質担保の観点で必要になる。

### 対応方針

HashiCorp公式のテストフレームワーク（`terraform test`）を使用し、モジュールごとに単体テストを実装する。`terraform test` はTerraform 1.6から正式サポートされており、実際にリソースを作成・検証・削除するE2Eテストと、リソースを作成せずに計画のみ検証するモックテストの両方に対応している。

テストの実装対象は以下のモジュールを優先する。

| モジュール | 検証内容 |
| --- | --- |
| VPC / サブネット | CIDRブロック・サブネット数・ルートテーブルの紐付け |
| セキュリティグループ | インバウンド・アウトバウンドルールの正確性 |
| ECSタスク定義 | CPU・メモリ・コンテナ定義の設定値 |

また、テストはGitHub ActionsのCIワークフローに組み込み、PRのたびに自動実行する構成を目指す。

### 優先度

中（現状のポートフォリオ規模では必須ではないが、モジュール品質の担保およびIaC実践スキルのアピールとして価値がある）

### 対応時期

未定
